# Recompiler design

Source: the arm64 slice of `GameAssembly.dylib` from the macOS release (v1.4.2). The same layout exists in the iOS build.

## 1. Translation (`tools/recomp/arm64_recomp.py`)

* Input: 212,294 functions in the `il2cpp` section, with boundaries from the metadata (`tools/analysis/function_table.py`).
* Each function becomes `void f_<addr>(Ctx& c)`. `Ctx` holds x0-x30, sp, v0-v31 and NZCV (`recomp/runtime/recomp_ctx.h`).
* Branches inside a function become `goto`. Calls to other recompiled functions are direct calls. Calls outside the set go to `CallImport`, and indirect calls/branches go to `CallIndirect` or an in-function `switch`.
* Memory operands are host addresses. The game image is loaded and rebased at `g_imageBase` (`recomp/runtime/macho_image.cpp`), so adrp/adr produce `g_imageBase + page`.
* AdvSIMD instructions use lane helpers in `recomp/runtime/recomp_simd.h`.
* Status: **all 212,294 functions translate**. The output compiles with MinGW, and the largest functions need an unlimited compiler stack. To do: decode jump tables instead of labelling every instruction in functions with `br`.

## 2. Verification (`tools/recomp/difftest.py`, `recomp/tests/difftest.cpp`)

Game functions with primitive-only signatures run in Unicorn (the reference) with random and edge-case inputs. The recorded results are compared bit for bit with the recompiled code in a Windows build.

* Status: 602 functions and 19,264 vectors, **all passing**.
* Coverage grows once the runtime is linked, because functions that call into libil2cpp can then be tested too (1,648 more candidates).

## 3. Runtime helpers

### Where the runtime is

The registration tables name 291,266 functions (generated code). `LC_FUNCTION_STARTS` lists more, and the rest of `__text` falls in two groups (`tools/recomp/gap_functions.py`):

* **Generated-code helpers that no table lists**: inline functions the compiler emitted out of line (NullCheck, InitializedTypeInfo, array `SetAt`, `__clang_call_terminate`, catch funclets after the last function). They operate on guest data like any game function, so they are translated as a second unit (`arm64_recomp.py --extra-table`, looked up by `FindFunction` and by `CallImport` before it gives up).
* **The runtime**, in link-order blocks: baselib helpers (0x2670), `il2cpp-api.cpp` (0xfcbe4), icalls + os + GC + zlib (0xff280), the vm/metadata/codegen objects (0x125318-0x1931a4), and outlined cold assertion paths (0x3f4458). Game code reaches the runtime only through `CallImport` handlers.

Self-contained runtime leaf code (Interlocked icalls, `Math::Pow`, zlib's inflate internals and `adler32`) is simply translated too: `leaf_closure.py` checks that its static call closure reaches nothing but itself and libc stubs.

### Handlers

147 runtime functions are called from game code besides the icalls:

* **64 out-of-line helpers of `codegen/il2cpp-codegen-il2cpp.cpp`** (0x192c54-0x1931a0). The linker kept them in source order; dead-stripped ones are gaps. Each is a short tail call, so its identity follows from its position plus its target (e.g. 0x192da8 -> 0x132e40, which `resolve_icall` uses for its MissingMethodException). They are bound to the native functions of the same name through `native_adapter.h`, a template that reads AAPCS64 arguments (x0-x7, v0-v7, aggregates up to 16 bytes in register pairs) and writes the result back. COM helpers abort with a message.
* **Internals called directly**: `Class::Init`, `ClassInlines::GetInterfaceInvokeDataFromVTableSlowPath`, `ScopedThreadAttacher` (constructed in the guest frame of reverse P/Invoke wrappers), `SetWriteBarrier`, the ThreadPool icalls and the MonoPosixHelper ZStream exports.
* **libc/libm stubs**: named from the indirect symbol table and generated by `gen_libc_imports.py`.

### Icalls

Unity 2020.3 binds corlib icalls at build time (`libil2cpp.icalls`), so the binary has no name table; 371 icall implementations are called directly. `icall_targets.py` names each target from the managed methods calling it. The method bound to an icall is a trampoline (a lone `b`), while other callers reach it through inlining, so trampolines decide; overloads are separated by matching the IL parameter kinds against the caller's C signature from Il2CppDumper. Eleven overloads that remain identical at that level are fixed by hand in `gen_icall_imports.py`, which emits `icall_imports.cpp` binding every address to the same function of the native libil2cpp.

## 4. Linking to the Windows runtime

* libil2cpp is built natively for Windows from the same Unity version. Its data structures are identical, so recompiled code reads and writes them directly.
* `CallImport(addr)` dispatches to generated bridges. Each bridge reads arguments from `Ctx` (AAPCS64: x0-x7, v0-v7), calls the native function, and writes x0/v0 back.
* Method pointers in `CodeRegistration` are replaced with native-ABI entry thunks generated from each method's signature (`script.json` has all of them). Invokers are handled the same way. `CallIndirect` maps a thunk address back to its recompiled function, so game-to-game calls stay direct.
* Icalls: `il2cpp_codegen_resolve_icall` returns a native Unity function. The `blr` in the icall wrapper is emitted as a typed native call using the wrapper's signature.

## 5. Exceptions

IL2CPP implements managed exceptions as C++ exceptions. The game code calls `__cxa_throw`, `__cxa_begin_catch`, `__cxa_end_catch` and `_Unwind_Resume`, and its landing pads are described by the LSDA (`__gcc_except_tab`) together with the compact unwind info.

Plan:

* From each function's LSDA call-site table, the translator wraps calls inside protected ranges as `try { call } catch (...) { ...; goto landing_pad; }`.
* At the landing pad, x0 holds the exception pointer and x1 the selector. The selector is computed by evaluating the LSDA action and type-filter entries against the thrown type, as the C++ personality routine does. If nothing matches and there is no cleanup, the exception is rethrown.
* `__cxa_throw` from game code throws a native C++ exception that carries the game exception object. `_Unwind_Resume` rethrows it, and `__cxa_begin_catch`/`__cxa_end_catch` manage the caught object.
* Exceptions thrown by the native libil2cpp (`Il2CppExceptionWrapper`) are caught by the same wrappers and presented to the landing pad the same way.
